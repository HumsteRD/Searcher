# Threat Scanner — состояние проекта

Windows-утилита проверки системы на угрозы. C++20 / Qt 6 (vcpkg, x64-windows),
CMake, MSVC. Интерфейс: русский и английский.

## Сборка

`cmake` не в PATH — он идёт с Visual Studio:

```
"C:/Program Files/Microsoft Visual Studio/18/Community/Common7/IDE/CommonExtensions/Microsoft/CMake/CMake/bin/cmake.exe" --build C:/test/ts2/build --config Release
```

vcpkg: `C:/dev/vcpkg`. Toolchain уже прописан в кэше сборки, передавать не нужно.

Приложение требует прав администратора (манифест). Запуск:

```
powershell -Command "Start-Process 'C:\test\ts2\build\Release\ThreatScanner.exe' -Verb RunAs"
```

Если линковка падает с LNK1104 — приложение запущено и держит exe.
Если включён трей, крестик только прячет окно; выходить надо из меню трея.

Приложение собрано как GUI, консоли нет. Сообщения Qt пишутся
в `%TEMP%\ThreatScanner-debug.log` — при падениях смотреть туда в первую очередь.

## Что сделано

**Ядро** — `Scanner` с восемью модулями (`IScanModule`), каждый в `src/core`:
реестр, файлы, процессы, сеть, задачи планировщика, скрипты, закрепление
в системе (WMI/hosts/службы). Порядок регистрации в `MainWindow` обязан
совпадать с `AppSettings::ModuleId` — по индексу отбираются включённые модули.

**Действия**: карантин (XOR-изоляция + метаданные), удаление, пропуск.
Для реестра и задач «карантин» = удаление, статус ставится `Deleted`, и кнопка
называется «Удалить запись» с подтверждением.

**Остальное**: VirusTotal (очередь 4 запроса/мин), история проверок с экспортом
отчёта, автоматизация (автозапуск, расписание, трей), обновляемая база сигнатур
(`signatures.json` в папке данных, добавляется поверх встроенных), справка.

**Дизайн-система** — `src/theme.h`, макеты в `design/`. Замкнутые шкалы:
7 размеров шрифта, отступы кратны 4, границы всегда 1px. Свои виджеты
в `src/ui`: фреймлесс-окно, градиентные кнопки, тумблеры, модальные окна.

## Грабли, на которые уже наступали

Не повторять — каждая стоила отдельного цикла отладки:

- **`winId()` в `nativeEvent` создаёт окно** → рекурсивное `CreateWindowEx`,
  ошибка 0x57 и зависание. Только `internalWinId()`.
- **Нативную настройку окна нельзя делать в конструкторе** — платформенного
  окна ещё нет. Только в `showEvent`.
- **Все указатели-члены инициализировать `nullptr`**: `changeEvent` и подобные
  приходят во время работы конструктора, до присваивания полей.
- **`ResizeToContents` не видит виджеты в ячейках таблицы** — ширину колонок
  с кнопками и пилюлями считать вручную по `minimumSizeHint()`.
- **`QTableView` по умолчанию переносит текст** — `setWordWrap(false)`.
- **Страницы с растущим числом карточек** — только через
  `PageHelpers::scrollablePageLayout()`, иначе layout сожмёт содержимое.
- **Пути из `QFileDialog` идут с прямыми слэшами**, из обхода каталога —
  с обратными. Перед сравнением нормализовать.
- **Qt не читает ICO с PNG-записями** — иконки в интерфейсе только из SVG
  через `Icons::fromResource`.
- **QSS не умеет**: градиентную обводку, `text-transform`, тени, анимации,
  позиционирование. Всё это делается своими виджетами и `QPropertyAnimation`.
- **Рекурсивное наблюдение за каталогом не доходит до `%TEMP%`.**
  `ReadDirectoryChangesW` с `bWatchSubtree = TRUE` на `%LOCALAPPDATA%`
  не даёт ни одного события из `%LOCALAPPDATA%\Temp`, хотя тот же Temp,
  открытый отдельным корнем, отдаёт всё. Точкой повторной обработки он
  не является — проверено. Поэтому вложенные корни не схлопываем,
  а повторы гасим окном склейки в `FileActivityWatcher`.
- **Синхронный ввод-вывод на одном дескрипторе идёт строго по очереди.**
  Поток чтения стоит в `ReadFile` именованного канала — и `WriteFile`
  из другого потока на том же дескрипторе не выполняется, пока чтение
  не завершится. Разговор в обе стороны встаёт намертво, причём тихо:
  обе стороны выглядят живыми. Дуплекс на одном дескрипторе возможен
  только через `FILE_FLAG_OVERLAPPED` с отдельным событием на каждое
  направление — это и делает `PipeChannel`.
- **Ложные срабатывания дороже пропусков.** Энтропия строки НЕ улика сама
  по себе (минифицированный JS даёт то же самое) — только усиление уже
  найденного поведения. Отбор в `ScriptScanner` идёт по сумме весов, порог 6.

## Разделение прав

Интерфейсу права администратора не нужны — их требует то, что он делает
с системой. Привилегированное уезжает в отдельный процесс `ThreatHelper`,
который поднимается через UAC и живёт ровно столько, сколько открыт канал.

Готов канал (`src/ipc`): протокол построчного JSON, `PipeChannel` с
перекрывающимся вводом-выводом, `HelperServer` в помощнике, `HelperClient`
в интерфейсе. Проверка — `ipc_test` (спросит UAC).

Что защищает канал и что нет:

- Имя случайное на каждый запуск, `FILE_FLAG_FIRST_PIPE_INSTANCE` —
  к чужому каналу с тем же именем помощник не присоединится.
- Список доступа: текущий пользователь, SYSTEM, администраторы.
- Подключившийся проверяется по учётной записи и пути к образу, обе
  проверки — по одному дескриптору процесса (иначе между ними номер
  процесса может достаться другому).
- Олицетворением проверять нельзя: `ImpersonateNamedPipeClient` работает
  только после того, как клиент что-то прислал, а проверять надо до
  первой команды.
- **От процесса того же пользователя это не защищает и не может.**
  В модели Windows всё под одной учётной записью равно в правах, и такой
  процесс может подменить сам файл приложения. UAC не является границей
  безопасности — писать в интерфейсе или в комментариях обратное нельзя.

Что уже за границей:

- **Проверка целиком** — `Scanner` со всеми модулями живёт в `ScanService`
  внутри помощника. Настройки едут с командой `start_scan`, а не читаются
  из реестра: помощник поднялся один раз, а пользователь мог поменять их
  позже. Ход работы возвращается событиями, `ScannerBridge` их только
  переизлучает — сигналы у него прежние, страницы не изменились.
- **Действия над угрозами** (`apply_action`) и **изменение карантина**
  (`quarantine_restore`, `quarantine_delete`). Читать список карантина
  интерфейс умеет сам: хранилище в `%ProgramData%` открыто на чтение.
- В опросе состояние отправляется **последним**, после статистики: на
  «проверка окончена» интерфейс пишет запись в историю, и счётчики
  к этому моменту должны быть свежими.

Манифест интерфейса — `asInvoker`. Проверено: приложение стартует без
запроса прав, UAC появляется в момент первой привилегированной операции,
**перетаскивание из проводника снова работает** (было в ограничениях как
неисправимое, пока окно идёт от администратора).

- **Сеанс песочницы** (`SandboxService`): `sandbox_run` / `sandbox_cancel`,
  стадии уходят событиями. Отчёт помощник сохраняет сам и возвращает путь —
  рабочую папку сеанса он же и удаляет, другого экземпляра отчёта нет.
  Интерфейс читает файл тем же кодом, что и отчёт, открытый вручную.

**Что из этого не проверено вживую.** Всё, что касается самой песочницы:
на домашней редакции её нет, и путь «команда → `WindowsSandbox.exe` →
отчёт → страница» ни разу не выполнялся целиком. Проверено только то,
что код собирается и что на системе без песочницы сеанс отказывается
стартовать с внятной причиной.


## Вердикт после проверки на чужом ПК — что чинить

Список от пользователя после установки на другую машину. Порядок —
от «инструменту нельзя доверять» к «некрасиво». Сначала ядро, потом
интерфейс целиком, а не по одному скриншоту: точечные правки по одному
экрану ломали соседние — так уже было трижды.

### Ядро поиска — главное

- **Сканируется малая часть диска.** Быстрая проверка — 1200 файлов,
  полная — 2000. Обход идёт по списку «горячих папок» (`SignatureDB::
  HotDirectories`), а не по дискам. Находки появились, только когда
  пользователь вручную указал «Загрузки». Нужен настоящий обход томов
  с исключениями, приоритетами и честной оценкой времени.
- **Не находит реальные образцы.** Скачанные для проверки логер и
  куки-грабер не задетектились даже при перетаскивании файла. Детект
  держится на именах, путях и почти пустом списке хэшей. Нужен разбор PE
  (импорты, секции, упаковщики) и нормальная база сигнатур.
- **Ложные срабатывания на легитимном ПО.** Помечались подписанные файлы
  Microsoft и NVIDIA, а также сторонние антивирусы. ЧАСТИЧНО ИСПРАВЛЕНО:
  из подозрительных путей служб убран `ProgramData`, добавлена проверка
  подписи через `SignatureVerifier` + `PublisherWhitelist`. Проверить, что
  та же защита стоит во ВСЕХ модулях, а не только в службах.
- **Кнопка «Пропустить» ведёт себя так, будто не работает.** Проверить
  весь путь: действие → статус → строка остаётся в списке с пометкой.

### Интерфейс — нужен один сквозной проход

Чинить не по одному экрану, а сразу все страницы, проверяя каждую на трёх
размерах окна (минимум 1100×720, рабочий 1280×800, развёрнутое).

- Текст не влезает, вылезает за края, элементы наезжают друг на друга.
- При изменении размера окна колонки и карточки должны перестраиваться,
  а не наползать. Сейчас поведение при уменьшении не проверялось вовсе.
- В справке произвольные отступы между блоками.
- Причины находок не переводятся на русский и написаны языком разработчика
  («строка N: ...»). Пользователю нужно, что файл делает, а не где это
  в коде. Статусы тоже приходят по-английски — ЧАСТИЧНО ИСПРАВЛЕНО
  (`setThreatStatus` переводит, цвет берётся по английскому ключу).

### Поведение

- **Двойной клик по расположению открывает проводник** с выделенным
  файлом. СДЕЛАНО. Полный путь лежит в `Qt::UserRole` ячейки, потому что
  отображаемый текст обрезан.
- **Перетаскивание одного файла запускает полную проверку.** Нужно
  проверять только этот файл и показывать вердикт по нему, а не гонять
  все модули.
- **Windows Sandbox не установлена — приложение молчит.** Нужна проверка
  наличия и подсказка с командой установки, а не пустая страница.

## Известные ограничения

- **Расписание в приложении работает, только пока открыто окно.** Для
  фоновой работы есть `ThreatService` (см. ниже), но интерфейса управления
  им пока нет — ставится и снимается он только командами помощника.

## Служба фоновых проверок

`ThreatService.exe` — единственное, что работает при закрытом окне.

**У службы нет командного канала, и это главное решение.** Помощник
принимает команды, потому что живёт под учётной записью пользователя
и ровно столько, сколько открыто окно. Служба работает под SYSTEM
постоянно — приём команд превратил бы её в постоянно открытую дверь
с полными правами. Настройку она только читает из `HKLM`
(`ServiceConfig`), результаты складывает в `%ProgramData%\ThreatScanner`.

Ставится и снимается через помощника (`service_install`,
`service_uninstall`, `service_status`, `service_configure`) — диспетчер
служб с непривилегированным процессом не разговаривает. Сама установка
делается кодом самой службы (`--install`), чтобы не держать две
реализации работы с диспетчером.

Проверено: сборка, `--status` без прав, отказ `--install` без прав
с внятной причиной, ответ на `service_status` через канал помощника.
Не проверено: реальная установка и срабатывание расписания.

Осталось: управление службой в настройках и показ её результатов
в истории — сейчас файл `service-scans.json` никто не читает.

## Динамический анализ: наблюдатель готов, изоляции нет

Сделано ядро наблюдения (`B9` в `CMakeLists.txt`), от интерфейса и от
песочницы не зависит:

- `BehaviorMonitor` — запускает цель в job-объекте с портом завершения,
  ведёт дерево процессов (путь и командная строка читаются из PEB),
  по окончании снимает всё дерево. Скрипты запускает через интерпретатор,
  и он же становится корнем дерева.
- `FileActivityWatcher`, `RegistryActivityWatcher` (слепок + диф по
  `RegNotifyChangeKeyValue`), `NetworkActivityWatcher` (опрос таблиц
  соединений с фильтром по PID дерева).
- `BehaviorReport` — события с меткой времени от старта, дерево процессов
  и **список ограничений**. Ограничения заполняются всегда и обязаны
  доехать до интерфейса: отчёт без них читается как полная картина.

Проверка: `dynmon_test` (консольная цель, Qt и прав администратора не
требует). Запускает безвредную мишень — файл в `%TEMP%`, значение
автозапуска с самоочисткой, дочерний процесс, соединение на собственный
слушающий сокет — и сверяет отчёт с ожиданиями.

```
"C:/Program Files/Microsoft Visual Studio/18/Community/Common7/IDE/CommonExtensions/Microsoft/CMake/CMake/bin/cmake.exe" --build C:/test/ts2/build --config Release --target dynmon_test
C:\test\ts2\build\Release\dynmon_test.exe
```

Проходит все проверки без прав администратора. `%WINDIR%\System32\Tasks`
и `%WINDIR%\Temp` при этом не открываются — в приложении, которое идёт
от администратора, они наблюдаются, но в отчёте недоступный каталог всё
равно отмечается отдельной строкой ограничений.

### Слой песочницы

- `SandboxEnvironment` — доступна ли Windows Sandbox и что именно мешает.
  Различает «домашняя редакция» (не чинится), «компонент не установлен»
  (чинится, и как — сказано) и «виртуализация выключена в прошивке».
  `ProductName` из реестра на Windows 11 врёт («Windows 10 ...»), поэтому
  редакция уточняется по номеру сборки.
- `WsbGenerator` — конфигурация сеанса. Внутри три отображённые папки:
  `C:\sample` и `C:\agent` только на чтение, `C:\report` на запись —
  единственный путь отчёта наружу. Сеть, буфер обмена, микрофон, камера,
  принтеры выключены. Порядок элементов — как в документации Microsoft:
  проверить чужой порядок на этой машине нечем.
- `ThreatAgent` — консольная цель, которая уезжает в песочницу. Запускает
  `BehaviorMonitor` и кладёт отчёт в JSON (`BehaviorReportJson`, запись
  без Qt, чтение на стороне приложения через `QJsonDocument`). Пишет
  через временный файл с переименованием: хост не должен увидеть половину.
  По ключу `--shutdown` гасит машину сразу после отчёта — иначе окно
  с работающим образцом остаётся висеть.
- `SandboxSession` — сеанс целиком: раскладка в данных приложения,
  копирование образца и агента, запуск, ожидание отчёта с отменой,
  разбор. Рабочая папка удаляется деструктором в любом случае — в ней
  лежит копия того самого файла, который считается опасным. Исключение
  одно: отчёт не удалось прочитать, тогда разбираться было бы не с чем.

Проверки (обе без прав администратора и без песочницы):

```
C:\test\ts2\build\Release\dynmon_test.exe            наблюдатель на мишени
C:\test\ts2\build\Release\dynmon_test.exe --wsb <папка>   генерация .wsb
C:\test\ts2\build\Release\sandbox_test.exe          отчёт туда-обратно
```

`sandbox_test` гоняет отчёт «структура → JSON → файл → структура» с
кириллицей, кавычками, слэшами и кодом возврата больше `INT_MAX`,
проверяет, что незнакомый тип события не ломает разбор и не исчезает,
и что на домашней редакции сеанс отказывается стартовать, объясняет
причину, не обещает несуществующей починки и не оставляет мусора.

Не проверено и здесь непроверяемо: примет ли конфигурацию сама Windows
Sandbox, сработает ли `ProtectedClient`, закроется ли машина по
`ExitWindowsEx` и погасит ли `TerminateProcess` виртуальную машину при
отмене (об этом сказано прямо в тексте отказа).

### Вердикт по поведению

`BehaviorVerdict` превращает ленту событий в список улик с весами и общий
уровень — лента из двух десятков строк без вывода это работа, переложенная
на пользователя. Сумма весов, пороги 6 и 10, как в `ScriptScanner`. Вес —
это цена ошибки: подмена отладчика или драйвер в `system32` весят 8 и тянут
вердикт в критический сами по себе, запись файла в `%TEMP%` весит 3 и в
одиночку порога не берёт. Проверки в `sandbox_test`.

Результат сеанса расходится по приложению из `SandboxPage::publishSession`:

- **Вердикт `HIGH` и выше даёт угрозу** по файлу на хосте — она уходит
  в общий список через `Scanner::Report`, и к ней применимы карантин и
  удаление, как к находке обычной проверки. Путь берётся тот, что выбрал
  пользователь: `report.target` содержит путь ВНУТРИ песочницы
  (`C:\sample\<имя>`), на хосте по нему ничего нет.
- **В историю попадает любой сеанс**, даже пустой: «проверили и ничего
  не нашли» — тоже результат. Режим `Sandbox`, объекты — число событий.
- **Отчёт сохраняется отдельно** в `<данные приложения>/sandbox/reports`,
  путь пишется в `ScanRecord::reportPath`, строка истории получает кнопку
  «Поведение». Рабочая папка сеанса удаляется вместе с копией образца, и
  без этой копии от наблюдения оставалась бы только выжимка находок.
  Держим последние 20 отчётов; кнопка показывается, только если файл ещё
  на месте — мёртвая кнопка врала бы о наличии данных.
- **В `Threat::evidence` кладётся SHA-256 образца**, иначе на строке
  поведенческой угрозы не работает проверка в VirusTotal: страница угроз
  берёт хэш именно оттуда.
- Отчёт, открытый из файла, никуда не расходится: он мог быть сделан на
  другой машине, и выдавать его за результат проверки этой нельзя.

Два правила, которые нельзя нарушать при правках:

- **Пустой результат — не справка о безопасности.** Текст так и говорит:
  «ничего примечательного не произошло, это не доказательство, что файл
  безопасен».
- **Образец, который не запустился, не судят вовсе** — иначе улики от
  чужой активности приписываются файлу, который и не работал.

### Страница «Поведение»

`SandboxPage`, пункт `Sidebar::Behavior` между карантином и журналом.
Порядок в `Sidebar::Page`, в `kPageTitles` и в порядке добавления страниц
в стек — один и тот же индекс, менять только все три сразу.

- Карточка доступности сверху. Если песочницы нет, она объясняет причину,
  а на домашней редакции прямо говорит, что включить нельзя, и что
  остальное приложение работает как обычно. Карточка выбора образца при
  этом целиком выключена — неработающей кнопки на странице нет.
- Сеанс идёт в своём потоке: `SandboxSession::Run` блокирующий. Стадии
  и завершение приходят в интерфейс сигналами через очередь. Деструктор
  отменяет сеанс и дожидается потока — страница пересоздаётся при смене
  языка, и сеанс в этот момент может идти.
- Блок ограничений показывается вместе с отчётом, а не прячется под
  ссылку. Фразы приходят из ядра английскими; постоянная часть двух из
  них («Наблюдались только эти каталоги: …») переводится по префиксу,
  хвост со списком путей остаётся как есть. Тем же способом переводятся
  приписки в колонке подробностей («код возврата», состояния TCP).
- Кнопка «Открыть отчёт» читает сохранённый JSON и рисует его как обычный
  результат, только статус честно говорит, что отчёт из файла. Песочница
  для этого не нужна — единственный способ увидеть отрисовку отчёта на
  машине, где сеанс запустить нельзя. Готовый отчёт для таких проверок
  делается так:

```
C:\test\ts2\build\Release\dynmon_test.exe   # пишет %TEMP%\ts-dyn-report.json
```

- **Числительные — через `TRN`.** В русском три формы, и правило не
  сводится к последней цифре: «21 процесс», но «11 процессов».

**Изоляции по-прежнему нет — на этой машине.** Код связан целиком, но
проверить его вживую можно только на Pro или Enterprise. `BehaviorMonitor`
сам по себе запускает файл там, где его позвали: вне `SandboxSession`
звать его для подозрительного образца нельзя.

**Машина разработки — Windows 11 Домашняя, Windows Sandbox на ней нет**
(`EditionID = Core`, `WindowsSandbox.exe` отсутствует). Всё, что можно
проверить без запуска виртуальной машины, проверено; живой прогон — нет.

Решения, принятые заранее:

- **Своей песочницы не делаем.** Запуск подозрительного файла в сеансе
  пользователя — это заражение, а не изоляция. Использовать **Windows Sandbox**
  через генерацию `.wsb`. Её нет в Windows Home — проверить редакцию
  и честно сказать пользователю, если недоступна.
- **Полной достоверности без драйвера ядра не будет.** В пользовательском
  режиме доступны: дерево дочерних процессов, изменения файловой системы
  (`ReadDirectoryChangesW`), реестра (`RegNotifyChangeKeyValue`), сетевые
  соединения процесса. Это меньше, чем Process Monitor, и об этом надо
  сказать прямо, а не изображать полноту.
- Наблюдение без изоляции смысла не имеет — это одна фаза, не две.

Отложено: служба Windows (она же решает и проблему с перетаскиванием,
если вынести привилегированные операции в отдельный процесс).
